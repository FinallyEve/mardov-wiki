Docker-Compose Configuration (Bridge Mode)\n\n### Canonical bridge-mode compose for linuxserver/plex\n\n```yaml\n---\nservices:\n  plex:\n    image: lscr.io/linuxserver/plex:latest\n    container_name: plex\n    # NOT network_mode: host — bridge mode with explicit ports\n    ports:\n      - \"32400:32400/tcp\"     # Primary — required\n      - \"8324:8324/tcp\"       # Plex Companion (Roku control)\n      - \"32469:32469/tcp\"     # Plex DLNA server\n      - \"1900:1900/udp\"       # DLNA/SSDP discovery\n      - \"32410:32410/udp\"     # GDM network discovery\n      - \"32412:32412/udp\"     # GDM network discovery\n      - \"32413:32413/udp\"     # GDM network discovery\n      - \"32414:32414/udp\"     # GDM network discovery\n    environment:\n      - PUID=1066\n      - PGID=0\n      - TZ=America/Chicago\n      - VERSION=docker\n      - PLEX_CLAIM=            # Only needed on FIRST start to claim server\n    volumes:\n      - /opt/media-stack/plex:/config         # CRITICAL — must persist\n      - /opt/media-stack/plex-transcode:/transcode\n      - /mnt/nas/movies:/movies:ro\n      - /mnt/nas/movies2:/movies2\n      - /mnt/nas/tv:/tv:ro\n    restart: unless-stopped\n```\n\n**Which ports are actually required:**\n- `32400/tcp` is the only mandatory port for Plex to function\n- UDP ports 32410-32414 are for GDM (local network discovery) — needed for LAN clients to auto-discover server without going through plex.tv relay\n- 1900/udp is DLNA — omit if you don't use DLNA clients\n- 8324/tcp and 32469/tcp are for Plex Companion and DLNA — optional\n\n**Key difference vs host mode:** In host mode, Plex binds directly to the host's NIC. In bridge mode, Plex sees only the container's virtual NIC (172.17.x.x or similar). This means Plex self-reports the wrong IP to plex.tv unless you override it.\n\n---\n\n## 2. ADVERTISE_IP: linuxserver/plex vs plexinc/pms-docker\n\nThis is the most common source of confusion.\n\n### plexinc/pms-docker (official image)\n\n**ADVERTISE_IP IS supported as a native environment variable.**\n\nThe official image reads `ADVERTISE_IP` on container startup and writes it directly into `Preferences.xml` as part of container init scripts. The format is:\n\n```\nADVERTISE_IP=http://192.168.1.200:32400/\n```\n\nNote the trailing slash — it is included in the official examples.\n\nFull docker run example from official docs:\n```\ndocker run -d \\\n  -p 32400:32400/tcp \\\n  -p 8324:8324/tcp \\\n  -p 32469:32469/tcp \\\n  -p 1900:1900/udp \\\n  -p 32410:32410/udp -p 32412:32412/udp -p 32413:32413/udp -p 32414:32414/udp \\\n  -e TZ=\"America/Chicago\" \\\n  -e PLEX_CLAIM=\"<token>\" \\\n  -e ADVERTISE_IP=\"http://192.168.1.200:32400/\" \\\n  -e ALLOWED_NETWORKS=\"192.168.1.0/24,192.168.0.0/24\" \\\n  -h plex-server \\\n  -v /opt/media-stack/plex:/config \\\n  -v /transcode:/transcode \\\n  -v /movies:/data \\\n  plexinc/pms-docker\n```\n\n### linuxserver/plex (lscr.io image)\n\n**ADVERTISE_IP IS NOT natively supported as an env var.** The linuxserver maintainers explicitly declined to implement it (GitHub issue #102, closed Oct 2019, revisited in issue #331, closed Oct 2022). Their stated reason: \"We're not in favor of modifying or generating the Plex preferences file.\"\n\n**What this means for your setup:** If you use `lscr.io/linuxserver/plex`, setting `ADVERTISE_IP` in the compose file does nothing. The variable is silently ignored. You must set remote access via one of these methods instead:\n\n1. **Plex GUI** (Settings → Remote Access → manually set) — this writes `customConnections` and `ManualPortMappingMode` to Preferences.xml automatically\n2. **Direct Preferences.xml edit** — edit while Plex is stopped, set attributes manually (see Section 4)\n3. **Container custom script** — use linuxserver's `/custom-cont-init.d/` mechanism to run a sed command on startup that patches Preferences.xml\n\nIf you want to use the `ADVERTISE_IP` env var workflow, switch to `plexinc/pms-docker`. Both images are equivalent in capability; plexinc's just has native env var support for bridge networking.\n\n---\n\n## 3. Bridge Networking: Binding and Container Network Config\n\n**Plex binds to the first listed network interface inside the container.** In a default bridge network, that's the virtual `eth0` with an IP in the Docker bridge subnet (172.17.0.0/16 or similar). Plex then reports this unreachable address to plex.tv.\n\n**Does Plex need to bind to 0.0.0.0?** No explicit binding configuration is required. Plex always binds to 0.0.0.0 inside the container (all interfaces). The problem is not binding — it's self-advertisement. Plex tells plex.tv \"I am at 172.17.0.2:32400\" which is unreachable from outside the host. The port mapping (32400:32400) makes the port reachable, but Plex doesn't know about Docker's NAT layer.\n\n**The fix:** Override what Plex advertises to plex.tv. This is what `ADVERTISE_IP` (plexinc) and `customConnections` (both images via Preferences.xml) do.\n\n**Special container network config for bridge mode:**\n- No special Docker network configuration needed beyond the default bridge\n- Do NOT use `--ip` to assign a static container IP — unnecessary complication\n- Do NOT use `network_mode: none` — Plex requires outbound internet access for licensing\n- macvlan networking (assigns container a real LAN IP) eliminates the self-advertisement problem entirely, but adds complexity\n\n---\n\n## 4. Preferences.xml — Correct Attributes for Remote Access\n\nThese are the relevant attributes in `Preferences.xml` for remote access behind NAT. Edit this file while Plex is **stopped**.\n\nLocation on your VM: `/opt/media-stack/plex/Library/Application Support/Plex Media Server/Preferences.xml`\n\n### Minimal working configuration for bridge + double NAT\n\n```xml\n<?xml version=\"1.0\" encoding=\"utf-8\"?>\n<Preferences\n  ...existing attributes...\n  ManualPortMappingMode=\"1\"\n  ManualPortMappingPort=\"32400\"\n  customConnections=\"http://192.168.1.200:32400\"\n  GdmEnabled=\"1\"\n/>\n```\n\n### Attribute reference\n\n| Attribute | Values | Effect |\n|-----------|--------|--------|\n| `ManualPortMappingMode` | `0` or `1` | `1` = disable UPnP/NAT-PMP auto-detection, use manual port. **Set to `1` when behind double NAT** since UPnP will never work across two NAT layers. |\n| `ManualPortMappingPort` | integer (default: 32400) | The external port Plex advertises to plex.tv for remote access. Must match the port forwarded on your outermost router. If BGW320 passes through to UDM Pro and UDM Pro forwards 32400, this should be `32400`. |\n| `customConnections` | comma-separated URIs | The URIs that Plex publishes to plex.tv so mobile/TV clients can find the server. **This is the key field for bridge networking.** Set to the VM's LAN IP. |\n| `GdmEnabled` | `0` or `1` | `1` = enable local network discovery (GDM/mDNS). Allows Plex apps on same LAN to find server without relay. Leave `1`. |\n\n### customConnections format\n\nThe value is a comma-separated list of URIs. For your specific setup (VM at 192.168.1.200):\n\n```\ncustomConnections=\"http://192.168.1.200:32400\"\n```\n\nIf you have a reverse proxy providing HTTPS, add both:\n```\ncustomConnections=\"http://192.168.1.200:32400,https://plex.yourdomain.com:443\"\n```\n\n**Do not use the Docker container IP** (172.17.x.x). Use the VM's host IP (192.168.1.200).\n\n**Do not URL-encode or escape the commas.** Plex reads the raw comma-separated value.\n\n### Note on PublishedServerUriOverride\n\nThis attribute is used for reverse proxy setups where you want to force a specific URI regardless of what Plex auto-detects. It is not needed for standard bridge networking. If you ever set it incorrectly, it overrides everything and can cause clients to be unable to connect.\n\n---\n\n## 5. Double NAT Port Forwarding — BGW320 + UDM Pro\n\nYour topology:\n```\nInternet → BGW320 (public IP 99.112.162.67 on WAN, 192.168.1.x subnet)\n         → UDM Pro (WAN: 192.168.1.91, LAN: 192.168.0.x subnet)\n         → Plex VM at 192.168.1.200\n```\n\nWait — your Plex VM is at `192.168.1.200`, which is on the BGW320's subnet, NOT behind the UDM Pro. Let me cover both scenarios.\n\n### Scenario A: Plex VM at 192.168.1.200 (directly on BGW320 subnet, UDM Pro is separate)\n\nIf the Plex VM is on the BGW320's 192.168.1.x subnet (not routed through the UDM Pro), then:\n\n**BGW320 port forward:**\n- External port: 32400 (TCP)\n- Internal IP: 192.168.1.200\n- Internal port: 32400\n- Protocol: TCP\n\n**UDM Pro:** No configuration needed — traffic goes BGW320 → Plex VM directly, UDM Pro is not in the path.\n\nThis is the simplest possible case. No double NAT for Plex traffic.\n\n### Scenario B: Plex VM behind UDM Pro (on 192.168.0.x or similar)\n\nIf Plex is behind the UDM Pro (on the 192.168.0.x network), then you have a true double NAT:\n\n**BGW320 port forward:**\n- External port: 32400 (TCP)\n- Internal IP: 192.168.1.91 (UDM Pro WAN)\n- Internal port: 32400\n- Protocol: TCP\n\n**UDM Pro port forward:**\n- External port: 32400 (TCP)\n- Internal IP: [Plex VM IP on 192.168.0.x]\n- Internal port: 32400\n- Protocol: TCP\n\nBGW320 login: `http://192.168.1.254` (AT&T BGW320 default gateway)\n\nBGW320 navigation: Firewall → NAT/Gaming tab (or Firewall → Port Forwarding depending on firmware version). Add rule.\n\nUDM Pro navigation: Settings → Firewall & Security → Port Forwarding.\n\n---\n\n## 6. BGW320 IP Passthrough — Does It Eliminate the Double NAT?\n\n### What IP Passthrough does\n\nWhen you enable IP Passthrough on the BGW320 and pin it to the UDM Pro's WAN MAC address:\n- The BGW320 passes the **public IP** (99.112.162.67) to the UDM Pro via DHCP\n- The UDM Pro's WAN interface gets the real public IP\n- The UDM Pro becomes the single NAT device for all traffic\n\n### Setup steps on BGW320\n\n1. Log in to `http://192.168.1.254`\n2. Navigate to Firewall → IP Passthrough\n3. Set Allocation Mode: **Passthrough**\n4. Set Passthrough Mode: **DHCPS-fixed**\n5. Passthrough Fixed MAC Address: **MAC address of UDM Pro's WAN port**\n6. Disable BGW320 firewall: Firewall → Packet Filter (clear all rules) AND Firewall → Firewall Advanced (set all to Off)\n7. Restart BGW320 (Device → Restart Device)\n8. Power-cycle UDM Pro (full power off, not just reboot)\n\n**Critical MAC address note:** Do not use the MAC shown in the UniFi controller (that's the LAN port MAC). You need the WAN port MAC. Easiest to find it: plug UDM Pro WAN into BGW320, wait for BGW320 to learn it via DHCP, then go to BGW320's Device → Device List, find UDM Pro's WAN MAC there.\n\n### After IP Passthrough is enabled\n\n- UDM Pro WAN IP becomes 99.112.162.67 (your public IP)\n- **You only need port forwarding on the UDM Pro** — one hop, not two\n- BGW320 IP Passthrough is a one-way flow: BGW320 still technically exists in the path but doesn't NAT (or should not, when configured correctly)\n- **Caveat:** BGW320 IP Passthrough is NOT true bridge mode. The BGW320 still has its own WAN IP. But for all practical purposes with a properly configured setup, you get single-NAT behavior and one-hop port forwarding.\n\n### Important known issue\n\nBGW320 IP Passthrough **does NOT persist reliably** — it can reset to Off after broadband restarts or firmware updates. This is a known AT&T firmware bug (documented in our existing network lessons). After any BGW320 restart, verify passthrough is still enabled. If it keeps resetting, use the Default Server / DMZ approach instead:\n\n**Alternative: BGW320 Default Server (DMZ)**\n- Firewall → DMZ → set to 192.168.1.91 (UDM Pro WAN)\n- This forwards ALL unsolicited inbound traffic to UDM Pro\n- More persistent than IP Passthrough\n- Still technically double NAT but functionally equivalent for port forwarding\n\n---\n\n## 7. Common Mistakes That Cause \"Server Not Available\"\n\nThese are ordered by frequency:\n\n### 1. ADVERTISE_IP silently ignored (linuxserver/plex)\nSetting `ADVERTISE_IP` in docker-compose with `lscr.io/linuxserver/plex` does nothing. The env var is passed to the container but no init script reads it. The fix: set `customConnections` via GUI or direct Preferences.xml edit.\n\n### 2. customConnections set to Docker bridge IP\nSetting `customConnections=\"http://172.17.0.2:32400\"` instead of `http://192.168.1.200:32400`. The Docker bridge IP is unreachable from outside the host. Always use the VM/host IP.\n\n### 3. ADVERTISE_IP includes quotes in the value\nIn docker-compose or docker run commands:\n```\n# WRONG — includes literal quotes in the value Plex sees\nADVERTISE_IP=\"http://192.168.1.200:32400/\"\n\n# RIGHT in docker-compose (yaml handles the quotes)\n- ADVERTISE_IP=http://192.168.1.200:32400/\n```\nIn yaml, `- ADVERTISE_IP=http://192.168.1.200:32400/` passes the value without quotes. If you write `- ADVERTISE_IP=\"http://192.168.1.200:32400/\"` in yaml, the yaml parser strips the outer quotes correctly. But in a raw shell `docker run` command, wrapping in single quotes avoids the shell eating the slashes.\n\n### 4. ManualPortMappingMode=\"0\" with broken UPnP\nWith double NAT (BGW320 → UDM Pro), UPnP requests never propagate properly across both NAT layers. Plex tries UPnP, fails, shows \"Not available outside your network\", and some clients fall back to relay. Fix: set `ManualPortMappingMode=\"1\"` and specify the external port explicitly.\n\n### 5. Port forwarded on UDM Pro but not on BGW320\nTraffic arrives from internet at BGW320. BGW320 sees no rule for port 32400, drops it. The UDM Pro port forward rule is never reached. Both hops must be forwarded unless IP Passthrough/DMZ is active.\n\n### 6. BGW320 IP Passthrough reset after broadband restart\nBGW320 firmware bug — passthrough mode reverts to Off after reconnect events. Plex worked before, stops working after ISP maintenance. Check passthrough status whenever remote access breaks suddenly. Use Default Server (DMZ) as a more persistent alternative.\n\n### 7. Port 32400 UDP not forwarded\nTCP 32400 is the main port. UDP ports 32410-32414 are for local discovery (GDM). For remote access, TCP 32400 is all you need. But if you forward 32400 TCP and forget UDP on GDM ports, local LAN clients may not auto-discover the server (they fall back to plex.tv lookup, which still works but is slower).\n\n### 8. Plex database locked during Preferences.xml edit\nIf you edit Preferences.xml while Plex is running, Plex may overwrite your changes when it next saves its state. Always stop the container before editing Preferences.xml:\n```bash\ndocker compose stop plex\n# edit Preferences.xml\ndocker compose start plex\n```\n\n### 9. Mobile app cached stale server address\nAfter fixing the configuration, mobile apps may have cached the old (broken) server address. Force the app to refresh: Settings → (Server) → Edit → Update address, or sign out and back in on the mobile app.\n\n### 10. Plex Relay confusingly shows as \"available\"\nPlex's own \"Remote Access\" panel shows green / \"fully accessible\" even when using relay. Relay means your traffic bounces through Plex's servers (limited to 2 Mbps on free accounts). True direct access requires `relay=\"0\"` connections in the resources XML. If your 4K streams buffer remotely even though remote access shows green, you're on relay.\n\n---\n\n## 9. Recommended Setup for Your Specific Case\n\nYour actual topology needs clarification. Correct docker-compose.yml for Bridge Mode\n\n```yaml\nservices:\n  plex:\n    image: lscr.io/linuxserver/plex:latest\n    container_name: plex\n    # NOT network_mode: host\n    ports:\n      - \"32400:32400/tcp\"     # required\n      - \"8324:8324/tcp\"       # Plex Companion\n      - \"32469:32469/tcp\"     # DLNA\n      - \"1900:1900/udp\"       # SSDP/DLNA discovery\n      - \"32410:32410/udp\"     # GDM local discovery\n      - \"32412:32412/udp\"\n      - \"32413:32413/udp\"\n      - \"32414:32414/udp\"\n    environment:\n      - PUID=1066\n      - PGID=0\n      - TZ=America/Chicago\n      - VERSION=docker\n      - PLEX_CLAIM=           # only needed on first claim\n    volumes:\n      - /opt/media-stack/plex:/config\n      - /opt/media-stack/plex-transcode:/transcode\n      - /mnt/nas/movies:/movies:ro\n      - /mnt/nas/tv:/tv:ro\n    restart: unless-stopped\n```\n\nOnly `32400/tcp` is strictly required for Plex to function. ADVERTISE_IP: The Critical Image Difference\n\n**`plexinc/pms-docker` (official image):** ADVERTISE_IP IS supported natively. The init script reads it and writes it to Preferences.xml automatically. Format:\n\n```\nADVERTISE_IP=http://192.168.1.200:32400/\n```\n\nNote the trailing slash — included in all official examples. The env var can be a comma-separated list of URIs.\n\n**`lscr.io/linuxserver/plex`:** ADVERTISE_IP IS NOT supported. The linuxserver maintainers explicitly declined to implement it twice (GitHub issues #102 and #331). The env var is accepted by the container but no init script reads it. Setting it in your compose file does absolutely nothing.\n\n**For linuxserver, your options to set the advertise IP are:**\n1. Use the Plex GUI (Settings → Remote Access) — this writes `customConnections` to Preferences.xml automatically\n2. Stop Plex, edit `/config/Library/Application Support/Plex Media Server/Preferences.xml` directly\n3. Use linuxserver's `/custom-cont-init.d/` mechanism to run a sed command on startup\n\n---\n\n## 3. Preferences.xml — Exact Attributes Needed\n\nEdit while Plex is **stopped** (`docker compose stop plex`). Path on your VM:\n`/opt/media-stack/plex/Library/Application Support/Plex Media Server/Preferences.xml`\n\nAdd or update these attributes on the `<Preferences>` element:\n\n```xml\nManualPortMappingMode=\"1\"\nManualPortMappingPort=\"32400\"\ncustomConnections=\"http://192.168.1.200:32400\"\nGdmEnabled=\"1\"\n```\n\n| Attribute | Value | Why |\n|-----------|-------|-----|\n| `ManualPortMappingMode` | `1` | Disables UPnP/NAT-PMP auto-detection. Set to `1` behind double NAT — UPnP won't work across two NAT layers. |\n| `ManualPortMappingPort` | `32400` | The external port Plex advertises to plex.tv. Must match what's forwarded on your outermost router. |\n| `customConnections` | `http://192.168.1.200:32400` | The URIs published to plex.tv so mobile/TV clients can find the server. Use the VM's host IP, not the Docker bridge IP (172.17.x.x). |\n| `GdmEnabled` | `1` | Enables local network discovery. Leave enabled. |\n\n`customConnections` accepts multiple comma-separated URIs:\n```\ncustomConnections=\"http://192.168.1.200:32400,https://plex.yourdomain.com:443\"\n```\n\n---\n\n## 4. Double NAT Port Forwarding — BGW320 + UDM Pro\n\n**Important topology note:** Your Plex VM is at `192.168.1.200`, which is on the BGW320's subnet (192.168.1.x). It is NOT behind the UDM Pro (which serves 192.168.0.x). This means for Plex, you have a **single NAT**, not a true double NAT:\n\n```\nInternet → BGW320 (99.112.162.67 WAN) → 192.168.1.200 (Plex VM)\n```\n\nThe UDM Pro is on 192.168.1.91 as a client of the BGW320, but Plex traffic never touches it.\n\n**You only need one port forward on the BGW320:**\n- Login: `http://192.168.1.254`\n- Navigate: Firewall → NAT/Gaming (or Port Forwarding depending on firmware)\n- Rule: External port 32400 TCP → Internal IP 192.168.1.200 → Internal port 32400\n\nNo configuration needed on the UDM Pro for Plex.\n\n---\n\n## 5. BGW320 IP Passthrough\n\nIP Passthrough only matters if you want Plex behind the UDM Pro (on the 192.168.0.x network). In your current layout with the VM on 192.168.1.200, it is irrelevant for Plex.\n\nIf you do enable IP Passthrough to move the UDM Pro to single-NAT:\n1. BGW320 → Firewall → IP Passthrough → Allocation Mode: **Passthrough**, Mode: **DHCPS-fixed**, MAC Address: UDM Pro's **WAN port** MAC (not the LAN MAC shown in UniFi controller)\n2.
